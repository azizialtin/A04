# November 2026 pilot protocol and rollout

This release adds the `pilot_20261116` flow. New studies created through the
admin/API default to bundled think-aloud with `X = 3`: participants complete all
assigned cases, then discuss the final three in their original order. The
post-test case counts toward X; if fewer cases exist, all are discussed. Block
mode remains available. Existing studies keep `legacy` and block mode.

Use a fresh study for the pilot. The standard-battery seed action does not
upgrade an existing instrument. Questionnaire structure can only be changed
before a study has sessions or responses.

## Run preservation and page order

At first login, each participant receives a pinned flow version, think-aloud
mode, count, block size and video sequence. If no video set or personal sequence
is assigned, the study's current videos and their phases are copied into the
participant's slots. A run that starts without videos remains empty. Later
uploads, phase edits and think-aloud settings affect future first logins, not
the case order of an existing run. Existing session pointers and historical
questionnaire answers are not remapped. The flow version cannot be changed
through the study edit endpoint.

For one pre-test case, five training cases and one post-test case, the default
pilot script has **69 pages** with in-app calibration disabled, or **70** with
calibration enabled. It contains:

1. Welcome; demographics and two CK self-assessments; CK intro and 13 tasks;
   PCK intro and tasks 1, 3 and 5; MESP intro and six tasks; SoSci pre-test.
2. Questionnaire-end, video-start and video-intro pages; seven cases, each with
   intro, video, diagnosis and case questionnaire.
3. Video-end and discussion-start pages; think-aloud for cases 5, 6 and 7;
   post-questionnaire intro, SoSci post-test and end page.

The exact list is asserted in `backend/tests/test_pilot_flow.py`. Case numbers
run continuously across the video phase. Video titles are excluded from the
participant session script and supervisor step-back labels.

## CK skip and expiry

An explicit skip is stored as
`{"lines":[0],"explanation":"","skipped":true}`, with response status
`skipped`. It is permitted only on questions with `allow_skip: true`. A normal
answer still requires valid positive code lines and an explanation. Neither an
empty answer nor an invalid line is silently treated as a skip.

The seven-minute deadline is server-authoritative. On expiry, the frontend
submits the current page to `finish-ck` with reason `timer_expired`; the server
checks the deadline, records the partial answer and closes the CK attempt,
then moves to the PCK intro. The participant sees a short notice. The supervisor
chord remains available. Late ordinary submissions cannot advance to another
CK page, and retries of an accepted submission/finish do not advance twice.

Expiry responses have status `partial`, and the questionnaire visit records
`timer_expired` plus the submitted snapshot. Invalid/incomplete line input is
not converted into a solved answer. Unvisited pages remain unanswered. CSV
consumers should distinguish `submitted`, `skipped` and `partial`; section
`pages_answered` counts completed submissions, while visit timing also covers
skips and partial pages.

## Migration and rollback limits

Alembic revision `f8b1c3d5e7a9` follows `e6a2b8c4d0f1`. It adds study settings
with legacy defaults and participant pin fields. Existing non-registered
participants, and any participants with sessions, are pinned to the legacy
flow. No saved step index, CK ID or questionnaire structure is rewritten.

Revision `a1d3f5b7c9e2` follows it and freezes the video sequence for existing
started runs. It preserves personal sequences and copies the current default
order and phases for runs without one, including marking empty runs as pinned.
It does not reconstruct an older sequence if videos had already been changed
before this migration. Apply migrations before restarting the matching backend.

Revision `b2e4f6a8c0d3` then adds the session's current questionnaire-visit
identity. The server records it on entry rather than inferring the current visit
from the participant's clock. Generic progress cannot leave CK until that visit
has a matching saved submission, and cannot jump over unanswered CK pages.
Existing visit histories and times are unchanged. The marker starts empty for
existing sessions; an older client using separate save/progress requests must
reload and enter a new visit if its visit predates the migration. The current
frontend's atomic save-and-advance and section-finish paths remain supported.

Revision `c3f5a7b9d1e4` adds nullable retry identities to notes and participant
events. Historical rows remain unchanged. New clients retain one UUID per
queued write, so a lost acknowledgement can be retried without duplicating the
snapshot or event. The server acknowledges an event only after its transaction
commits; the note and its `note_saved` event commit together. Apply this migration
before starting the matching backend. A downgrade removes retry identities but
retains the collected notes and events.

Generic progress now also requires saved answers on non-CK questionnaires,
diagnoses and case-outro batteries. Normal submission and supervisor review
remain available; an API request cannot jump across unanswered pages. Note
drafts are retained locally while typing, flushed before case completion and
recovered on reload. Handoff to the next participant waits for the current
participant's queued writes, including after an end-page reload.

The pilot-flow migration (`f8b1c3d5e7a9`) changes four exact stock case-outro
strings only in studies without any sessions or questionnaire responses:
singular-case effort wording and the two approved authenticity statements.
Custom wording is preserved.

Downgrading `f8b1c3d5e7a9` refuses to remove the flow fields once any participant
is pinned to the pilot. Even before a pilot run starts, downgrade does not remove
seeded pilot questionnaires or reverse the stock-wording refresh; it is not a protocol
rollback. Restore a compatible pre-release database and application backup when
reverting those data changes. Existing started studies retain their questionnaire
content, although shared UI fixes such as hiding video titles apply to both
flows.

Downgrading `a1d3f5b7c9e2` retains copied video slots. It refuses to remove the
pin marker while an empty pinned run exists, because doing so could add later
study videos to that run. Restore a compatible backup when that rollback is
needed.

## Deployment checklist

These are deployment steps; deployment and lab acceptance have not been
performed as part of this implementation. Follow the environment-specific
[deployment notes](DEPLOY.md) for infrastructure and configuration.

1. Back up the database and durable media, and record the current application
   and Alembic revisions. Capture a representative legacy run's saved pointer
   and page list for comparison.
2. Run the release checks against an isolated test database. Build the matching
   backend and frontend, and apply `alembic upgrade head` before the new backend
   serves traffic. Deploy both application components together.
3. Confirm a legacy run resumes on the same page with the same ordering. Create
   a fresh pilot study and verify bundled mode with X=3, the intended video
   sets, SoSci URLs, questionnaire content and lab capture configuration.
4. Walk through the pilot on a lab device: verify the seven-case sequence,
   video rail labels/code layout, CK skip and actual seven-minute expiry,
   PCK exact-two validation, fixed MESP order and the final three replays.
   Include gaze/screen/audio capture and SoSci handoffs in lab acceptance.
5. Export the test run and inspect MESP IDs, CK skip/partial statuses, section
   timing and pinned participant settings before collecting pilot data.

## Verification

Backend regression coverage includes the exact 69-page script, count variants,
pinning, legacy compatibility, explicit skips, deadline enforcement, idempotent
retries, selection limits, content provenance and a real PostgreSQL migration
test. With `TEST_DATABASE_URL` set to an isolated disposable database, run from
`backend/`:

```sh
.venv/bin/pytest tests/test_pilot_content.py tests/test_pilot_flow.py \
  tests/test_migration_pilot.py tests/test_study_content.py \
  tests/test_study_content_import.py
```

Run the full backend suite for release verification. From `frontend/`, run
`npm test`, `npm run typecheck`, `npm run lint` and `npm run build`. The real API
walkthrough is `npm run e2e -- e2e/pilot-flow.spec.ts`; its database, account and
server prerequisites are documented in [the E2E guide](../frontend/e2e/README.md).
